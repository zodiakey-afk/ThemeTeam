# Agent Office 管理应用需求分析

版本：v1.2（2026-09-08，《主题医院》风格已确认，其余需求细节待确认）

当前实现核验见 [progress-assessment.md](progress-assessment.md)。第 1-9 节是产品长期目标，不代表已实现；本轮增量范围、可测试验收及待确认事项以第 10 节为准。专项草案评审见 [office-canvas.md](office-canvas.md)，后续计划见 [plan.md](plan.md)。

## 1. 产品目标

本产品是一个面向单机、单租户场景的本地化 Agent 管理应用。核心目标不是做一个纯列表式的 Agent 控制台，而是把 Agent 的状态、协作、任务流转、文档沉淀和模型配置放进一个可视化的“虚拟办公室”中，让用户可以像经营一间团队办公室一样管理多个 Agent。

办公室画布的 UI、视觉与交互明确以游戏《主题医院》为主要参考：固定等轴测的连续房间、走廊与门洞，易识别的人物动作、家具用途、头顶短气泡和对象操作反馈。画布必须像可运行的经营模拟空间；现代主题仅改变周边 DOM 面板皮肤，不取消该场景基准。素材使用原创或合法授权资源。

## 2. 范围与优化原则

### 2.1 范围

- 单机优先，数据默认本地化存储。
- 支持一个老板视角管理多个团队、多个 Agent。
- 支持聊天、会议、任务、文档、模型配置、知识库和工具接入。
- 支持随团队规模增长动态扩容办公室区域。
- 支持桌面端打包，后续可扩展离线模型。

### 2.2 优化原则

- 业务后端建议统一为 `FastAPI + Python worker`，避免同时维护两套业务后端栈。
- 视觉系统建议统一为“办公室画布 2.5D 游戏化视图 + 像素经营桌面外壳 + 现代信息面板（可切换主题）”的组合，不要把界面做成纯企业后台列表页。
- 多 Agent 编排建议以 `LangGraph` 为主，`AutoGen` 仅作为后续兼容或实验适配层。
- `MCP` 解决的是工具接入协议，不等同于执行沙盒；建议把“工具适配层”和“执行沙盒”分开设计。
- 2.5D 体验建议用等距 2D 资产与分层视差来实现，不要在早期直接引入重型 3D。
- `Mem0` 更适合作为记忆提取与归档层，原始知识检索仍建议由 `SQLite + ChromaDB + 文件系统` 承担。

## 3. 用户角色

- 老板 / 管理员：配置模型、审批高风险动作、查看团队总览。
- Team Leader：拆解任务、召集会议、派发子任务、查看团队执行状态。
- Agent 使用者：创建、编辑、部署和管理单个 Agent，观察执行结果。
- 只读观察者：查看状态、文档与历史记录，不参与操作。

## 4. 核心使用场景

### 4.1 初始化团队

用户创建工作区后，系统自动生成初始三人组：PM Agent、开发 Agent、测试 Agent，并分配到初始工位。

### 4.2 招聘与履职

用户从全局模型池中选择“大脑”，绑定工具与权限，重命名 Agent，选择皮肤，分配座位，完成上岗。

### 4.3 任务流转

用户在任务看板创建需求，或从聊天 / 会议中提炼任务，任务在 To Do / In Progress / In Review / Done 间流转。

### 4.4 多 Agent 讨论

用户在会议室召集多个 Agent 进行脑暴、评审、争议解决与总结，必要时由 Leader 或 Moderator 进行轮次控制与摘要收束。

### 4.5 成果归档

会议纪要、PRD、技术方案、测试报告和任务产物自动归档到文档中心，并与 Agent、任务、会议建立关联。

### 4.6 办公室扩容

当座位或团队规模达到阈值时，系统解锁新房间或新楼层，并允许按团队或部门快速聚焦。

## 5. 功能需求

### 5.1 虚拟办公室画布

- MUST：以《主题医院》式固定等轴测经营模拟布局呈现老板办公室、工位区、会议室、休憩区，用半高墙、门洞、连续走廊、家具和人物建立空间。房间不得以独立矩形卡片替代，状态标签不得替代人物；外壳与信息面板可切换皮肤，默认场景保持同一基准。
- MUST：支持点击房间聚焦、缩放、平移与快速导航。
- MUST：支持 Agent 以独立人物形象在办公区内占位、移动与状态显示，人物轮廓必须可识别，不应只是抽象圆点或标签。
- MUST：办公区中的 Agent 必须优先以人物形象呈现，状态标签只能作为辅助信息，不能替代人物本体。
- MUST：支持全局主题切换，至少包括像素经营桌面（默认）、现代 2D / 2.5D、极简网格三种视觉模式。
- SHOULD：支持房间级灯光、气泡、状态标记、移动路径和轻量动画。
- SHOULD：支持团队/部门选择器，切换后画布自动平滑聚焦。
- SHOULD：支持镜头缩放、平移、跟随选中 Agent、房间聚焦和快速返回总览。
- SHOULD：支持房间热点、路径预览、层级遮挡、视差和轻量阴影，以增强画布的游戏感。
- SHOULD：支持门洞、楼梯、走廊的过渡动画和合法落点高亮，不让移动显得像瞬移。
- SHOULD：支持状态密度高时的自动层级排序，让焦点人物始终可读。
- SHOULD：支持办公区中的人物朝向、队列、围站、让位和停留等空间关系表达，尽量减少人物重叠。
- SHOULD：支持在房间边界、门洞、工位和会议桌上提供明确锚点，保证移动、停靠和协作落位清晰可见。
- COULD：支持小地图、收藏房间和自定义布局。

### 5.2 Agent 管理

- MUST：支持创建、编辑、停用、删除 Agent。
- MUST：支持角色模板、名称、头像/皮肤、模型、工具、权限与工位绑定。
- MUST：创建 Agent 时必须提供可选的人物形象库，用户可在预设角色、配色、头部特征、服装风格之间选择。
- MUST：创建流程中要能直接预览人物形象在办公区中的站立、行走与工作效果，而不是只看静态头像。
- MUST：支持初始三人组自动部署。
- MUST：支持 Team Leader 的任命与撤销。
- SHOULD：支持成长解锁式晋升机制，但晋升结果必须与权限策略解耦；形象层可提供解锁式皮肤、表情和动作包。
- SHOULD：支持人物形象的长期可追踪性，同一 Agent 在不同房间、不同状态下应保持统一识别特征。
- COULD：支持 Agent 个性标签、偏好与工作风格配置。

### 5.10 角色形象与动效

- MUST：每个 Agent 都必须对应一个可视化人物形象，并在办公室画布中以统一的 sprite 或等价动画资产呈现。
- MUST：覆盖 Idle、Walking、Working、Thinking、Talking、In-Meeting、Sitting、Standing、Blocked 等表现，并提供 Offline/Paused 的可识别回退；业务活动、移动、姿态和发言覆盖层应分离，不能混为单一枚举。
- MUST：在工作、协作、会议、等待、阻塞等状态之间切换时，人物需要有明确的移动与朝向变化，而不只是静态闪烁。
- SHOULD：支持从 Agent 创建流程中直接选择角色形象，并在创建完成后保持该形象的长期可见性。
- SHOULD：支持面向方向、气泡、点头、挥手、围站、靠近工位、离开工位等细粒度动效。
- SHOULD：支持人物形象的可配置部件体系，例如头部、发型、服装、配色、配件和基础姿态，以便在保留统一风格的前提下做差异化。
- SHOULD：支持工作、移动、对话、会议和等待等动作循环的平滑过渡，动作切换时避免明显跳帧。
- SHOULD：支持协同场景中的群组编队效果，例如围桌、半圆站位、白板前聚集和发言轮换。
- COULD：支持不同部门或角色模板的专属动作包、季节皮肤和主题活动皮肤。
- COULD：支持表情包、情绪波动和临时强调动作，用于提示阻塞、庆祝、确认和反对。

### 5.3 聊天与会议

- MUST：支持 1v1 私聊。
- MUST：支持会议室中的多 Agent 群聊与轮次控制。
- MUST：支持 Moderator 总结、轮次上限和超时中断。
- MUST：支持在聊天或会议中直接创建任务或引用文档。
- SHOULD：支持 Leader 发起会议与任务拆解。
- COULD：支持争议观点并列展示与自动结论候选。

### 5.4 任务看板

- MUST：提供 To Do / In Progress / In Review / Done 四列基础流转。
- MUST：支持任务创建、拆解、指派、优先级、截止时间和状态变更。
- MUST：支持从聊天、会议和文档中生成任务。
- SHOULD：支持依赖关系、阻塞状态和回收重试。
- SHOULD：支持 Leader 对主任务进行自动拆分并派发子任务。
- COULD：支持拖拽式排期和工位关联。

### 5.5 团队文档中心

- MUST：按 PRD、技术架构、测试报告、会议纪要等分类归档。
- MUST：支持文档预览、版本记录、来源追踪与关联跳转。
- MUST：支持自动生成和自动归档。
- SHOULD：支持目录树、标签与全文检索。
- COULD：支持拖拽导入文件、批注和审批流。

### 5.6 全局模型配置

- MUST：统一管理 API Key、Provider、Model Profile 与预设模型池。
- MUST：支持招聘时直接下拉选择模型。
- MUST：支持不同模型的能力标签、费用标签、上下文长度与可用工具范围。
- SHOULD：支持按团队、角色或任务类型绑定默认模型。
- COULD：支持本地模型、云模型和混合模式共存。

### 5.7 知识库与记忆

- MUST：支持公司级、团队 / 项目级、Agent 私有记忆三层隔离。
- MUST：支持与文档中心自动同步。
- MUST：支持记忆抽取、回写、检索与权限隔离。
- SHOULD：支持显式记忆和隐式记忆分层。
- COULD：支持记忆推荐、人审确认和遗忘机制。

### 5.8 办公室扩容

- MUST：当容量、任务量或团队规模达到阈值时触发扩容建议。
- MUST：支持解锁新房间或新楼层。
- SHOULD：支持按部门扩容和按团队聚焦。
- COULD：支持装饰性扩容奖励与成长徽章，但不影响核心流程。

### 5.9 审批与安全

- MUST：对敏感操作提供老板审批或确认机制。
- MUST：API Key 本地加密存储，默认遮罩展示。
- MUST：记录关键动作审计日志。
- SHOULD：仅对高风险动作打断流程，避免无谓弹窗。
- COULD：支持审批模板与批量授权。

## 6. 非功能需求

- 本地优先：默认不依赖外部服务即可打开、查看和管理本地数据。
- 响应性：常规 UI 操作应保持流畅，画布交互应优先保证 60fps 体验目标。
- 动效性能：当多个 Agent 同时移动、交流或进入会议状态时，画布仍应保持可读、不卡顿且不发生明显穿模或文字重叠。
- 可恢复性：应用重启后应能恢复 Agent、任务、文档和事件状态。
- 可扩展性：支持增加新的角色模板、模型 Provider、工具适配器和主题皮肤。
- 可观测性：需记录任务、会议、模型调用、审批与文档生成事件。
- 安全性：工具调用、文件写入和模型密钥管理必须可控、可审计。

## 7. 边界与不做事项

- 不做多租户 SaaS 级账号体系作为首期目标。
- 不做强依赖云端协作的实时多人编辑作为首期目标。
- 不做重型 3D 场景作为首期目标。
- 不追求 Agent 完全自治，关键动作必须保留 Human-in-the-Loop。
- 不把 Node.js 与 FastAPI 同时作为业务后端长期并行维护。

## 8. 成功标准

- 用户能在单机环境完成从建团队、配模型、招 Agent、派任务、开会议到归档文档的完整闭环。
- 画布状态与后台执行状态一致，用户可直观看到 Agent 处于 Idle、Working、Thinking、In-Meeting 等状态，并能看到其在办公区内的移动与交流。
- 用户在创建 Agent 时可以直接选择人物形象，创建后的 Agent 会以独立角色形象出现在办公区。
- 用户能够在办公区里一眼分辨不同 Agent 的身份、状态和去向，且移动、交流和协作过程可被连续看见。
- 办公室扩容、任务流转和文档归档能在不中断主流程的前提下自动发生。
- 本地数据、模型配置与审计记录在重启后可恢复。

### 10.3 NFR 候选验收阈值
