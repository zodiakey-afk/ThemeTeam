## E. 紧接着的开发批次

**下一批建议范围：W00 剩余确认 + W00V 新视觉稿 + W01-W06 原型加固与办公室 PoC。** 后端 W07 可在接口确认且资源允许时并行预研，会议、知识和桌面打包后置。

### 当下具体从哪里开始

1. **准备项：完成 W00 的剩余确认。** 复用已明确的《主题医院》方向，确认首批范围/NFR，冻结该批验收及接口边界，不重做全产品需求分析。
2. **第一个代码任务：W01 测试与数据隔离。** 从 `tests/test_store.py`、`tests/test_server.py` 和 `themeteam/web/server.py` 的 STORE 注入边界入手，必要时调整 `store.py` 的构造入口；测试使用临时存储、每例独立实例，连续两次通过且真实 JSON hash 不变。
3. **并行视觉任务：W00V。** 用统一合法素材制作总览、人物/工位近景和“选中 -> 走廊行走 -> 入座 -> 状态反馈”分镜；先评审空间和人物，不直接润色历史矩形 SVG。一个人负责时先完成 W01，再安排视觉准备与 W02。
4. **基础加固：W02。** 关闭已知静态路径越界、未转义内容、非法状态/目标、伪审批与重复归档；新增验收规格先于修复实现，保护旧数据兼容性。
5. **画布实现：W03/W04 -> W05 -> W06。** 建 React/Phaser 状态桥，加载地图与人物资产，先实现相机/选中/遮挡，再实现四向行走/停靠/气泡和面板联动。只有通过 TH 标准与运行截图/动作验收，才算 M1 完成。

建议的首个可见交付不是完整医院经营游戏，而是：**同一办公室内，3 位可辨认的 Agent 能被选中，经走廊和门洞移动到工位，入座工作，右侧详情和底部任务区保持一致。** 单个接口或静态效果图不足以完成该交付。

演示验收脚本：打开现有数据的只读导入视图 -> 看到 3 位不同人物 -> 导航聚焦 -> 打开详情 -> 缩放/平移 -> 指定合法锚点移动 -> 经门洞落座 -> 在模拟状态变化中看到 Working/Thinking/Blocked -> 切换底部看板 -> 返回画布上下文不丢。最后展示不合法落点、缺素材和断连空态，不能只有成功路径。

PoC 用模拟状态只证明画布与 UI，**正式 MVP 仍需 W07-W10 的真实调用与持久化闭环**。如果资产验证失败，先调整选型/范围并回到相应门禁，不将新需求塞进旧 SVG 原型继续扩展。

| 单文件存储/测试写真实数据 | 数据损坏、测试结果不可信 | W01 先隔离，W07 显式备份迁移；后端/QA |
| 上传、模型输出、伪审批 | 越权、XSS、文件泄露 | W02 先补安全边界，M4 独立审查；安全评审人 |
| 扩容/多团队一次做完 | 范围膨胀、性能指标失真 | 单团队先验收，100 人仅压力画像；产品负责人 |

### DoD 与门禁

- 需求细节及 NFR 人工确认，设计/契约/计划按门禁冻结；每项提交可追溯到 OC 和 WBS。
- 新依赖有精确版本/lockfile、漏洞与许可证检查；不在运行时下载核心资产或脚本。
- 类型/构建、冻结 BB、隔离回归、影响与发散测试通过，失败均分级并闭环；不能用 9 个旧测试替代新增验收。
- 桌面与移动实测无空白场景、缺图或不可访问控件；性能有基准、样本与分位数，不能仅写“60fps”。
- M1 必须有 VIS-01 至 VIS-04 的视觉输入评审和 VIS-05 的真实运行证据，TH-01 至 TH-06 均有结论；代码构建成功不代替《主题医院》风格验收。
- 持久化/事件/权限相关项有故障注入、数据备份/回滚证据；安全及中高风险修改有独立评审。
- 每批附修改报告、已知限制、回滚方式与知识回写；最终负责人确认前运行不关闭。当前 G1-G7 均无正式通过记录。

## 历史计划 v1.0（保留，不再作为当前排期）

## 1. 总体策略

建议采用“先闭环、后扩展、再打磨”的顺序推进。第一阶段先把单机本地闭环跑通，第二阶段强化具身交互和多 Agent 协同，第三阶段补齐文档与知识能力，第四阶段再做桌面化封装和体验优化。

如果要进一步降低风险，建议在正式 Phase 1 前加一个 3 到 5 天的 Sprint 0，用来冻结信息架构、主题规则、数据模型和技术选型。

## 2. 建议里程碑

### Sprint 0：需求冻结与架构预研

目标：把最容易反复改动的部分先定住。

交付物：
- 页面结构草图
- 核心实体清单
- 事件总线与存储方案
- 模型配置和权限边界
- 办公区视觉基调、角色形象体系和动画规则草案

验收标准：
- 需求、交互和技术边界没有明显冲突。
- 已明确主后端、编排引擎和存储栈。

测试计划：
- 评审测试：逐条核对需求、设计、数据模型和状态机是否相互一致。
- 原型测试：用静态稿验证画布布局、信息密度和导航逻辑是否合理。
- 风险测试：整理高风险点、未决问题和后续依赖，确认是否会阻塞 Phase 1。
- 通过标准：所有核心争议点都有明确决议，Phase 1 可以进入实现。

### Phase 1：单机 MVP 核心引擎与全局设置（第 1 - 3 周）

目标：完成“模型配置 + 初始三人组 + 基础任务流转”的最小闭环。

核心工作：
- 搭建 FastAPI 主服务与 WebSocket 实时通道。
- 建立 SQLite 数据层与审计日志。
- 接入 LangGraph 的单 Agent 任务流。
- 完成全局模型配置、Agent 招聘、重命名与工位绑定。
- 完成 2D 画布、老板办公室和初始工位渲染。
- 完成基础任务看板与状态流转。
- 完成 Agent 创建页中的形象选择、静态预览和落位展示。

验收标准：
- 用户能创建团队、配置模型、部署 PM / 开发 / 测试三人组。
- 任务能从创建到完成全程可追踪。
- 画布能正确反映 Agent 状态和座位归属。
- 创建后的 Agent 至少能以稳定的人物形象出现在办公室中，并能区分基础模板。

测试计划：
- 单元测试：覆盖 Agent 创建、模型配置、任务状态机、持久化写入和基础权限校验。
- 集成测试：验证 SQLite、WebSocket、LangGraph 单 Agent 流与前后端联动。
- 冒烟测试：完整跑通“创建工作区 - 招聘三人组 - 创建任务 - 完成任务 - 刷新页面恢复”的闭环。
- 非功能测试：检查首屏加载、页面重绘和画布基础 FPS 是否达到可用水平。
- 通过标准：核心 CRUD、状态流转和页面恢复稳定可用。

### Phase 2：具身协同、会议室与团队扩容（第 4 - 6 周）

目标：实现“召集开会 + 多 Agent 脑暴 + 动态扩容 + Leader 机制”。

核心工作：
- 构建会议室 GroupChat 图，支持 Moderator 与轮次限制。
- 实现 Team Leader 的任务拆解和派发权限。
- 增加办公室扩容机制，新房间或新楼层可被解锁。
- 将默认主题统一落到像素经营桌面风格，并让任务板与聊天窗也遵循同一套默认视觉语法；补齐基础角色动画。
- 实现团队选择器和画布快速聚焦。
- 实现 Agent 在工位、门洞、会议桌和白板之间的移动、落位和围站动画。
- 实现 Talking、Thinking、Working、In-Meeting 等关键状态的过渡动效。

验收标准：
- 可以在会议室中发起多 Agent 讨论并产出摘要。
- Leader 能把主任务拆成多个子任务并派发给成员。
- 扩容后画布能平滑过渡到新增空间。
- 多个 Agent 同时移动或协同时，画布仍然能看清谁在去哪里、谁在对话、谁在等待。

测试计划：
- 单元测试：覆盖 Leader 权限、会议轮次限制、扩容触发条件和主题切换配置。
- 集成测试：验证多 Agent 群聊、Moderator 总结、任务拆解与派发、扩容事件广播。
- 交互测试：检查会议进入/退出、房间聚焦、动画切换和扩容过渡是否连贯。
- 回归测试：确保默认主题、主题切换和会议流程不会破坏 Phase 1 的任务板与模型配置。
- 通过标准：会议、扩容和 Leader 流程的关键路径稳定且无明显状态错乱。

### Phase 3：团队文档中心与三层记忆库（第 7 - 9 周）

目标：实现“成果自动归档 + 文档中心 + 知识沉淀”。

核心工作：
- 接入 ChromaDB 和记忆抽取管线。
- 建立公司 / 团队 / Agent 三层知识隔离。
- 增加 MCP 或本地沙盒工具适配层。
- 完成文档中心、分类归档、预览、搜索和关联跳转。
- 增加老板审批弹窗和高风险动作确认。

验收标准：
- 会议纪要、PRD、架构文档和测试报告可自动生成并归档。
- 记忆可以按层级检索，且敏感记忆支持人审。
- 文档与任务、会议、Agent 之间能互相跳转。

测试计划：
- 单元测试：覆盖文档分类、版本号、记忆作用域、审批规则和检索排序。
- 集成测试：验证会议/任务输出进入文档中心、Chroma 索引写入、MCP 或沙盒工具调用边界。
- 安全测试：检查敏感内容是否需要审批、审计日志是否完整、工具权限是否越权。
- 回归测试：验证文档预览、关联跳转和搜索不会影响任务板与会议功能。
- 通过标准：文档归档、记忆隔离和审批链路可稳定复现且可追溯。

### Phase 4：桌面客户端打包与体验打磨（第 10 周 +）

目标：交付开箱即用的本地个人生产力工具。

核心工作：
- 使用 Tauri 或 Electron 封装桌面端。
- 支持本地 Ollama / vLLM 等离线模型接入。
- 优化动画、渲染性能、响应速度和错误恢复。
- 增加 token 消耗、任务吞吐和团队运行情况看板。
- 打磨办公室空间中的人物识别度、协同过场和视觉节奏。

验收标准：
- 用户能够独立安装并离线运行核心功能。
- 本地模型和云模型都能稳定切换。
- 打包版本启动后可恢复本地数据和配置。
- 办公区的人物动画和协同动作在常见分辨率下保持清晰、连贯、不过度遮挡。

测试计划：
- 安装测试：验证首次安装、升级安装、卸载重装和数据保留是否正常。
- 兼容性测试：验证不同操作系统目标包、离线模型和云模型切换是否稳定。
- 性能测试：检查启动时间、长会话内存占用、复杂办公室画布渲染和持续任务吞吐。
- 回归测试：确保打包后不破坏 Phase 1 到 Phase 3 的核心功能和数据恢复能力。
- 通过标准：桌面端可稳定安装、启动、切换模型并恢复既有数据。

## 3. 推荐实施顺序

1. 先做信息架构与数据模型，再做画布与交互。
2. 先实现“显示状态”，再做“动作动画”。
3. 先做单团队闭环，再做扩容与多团队选择。
4. 先做自动归档的最小版本，再补全文档检索和审批。
5. 先保证本地稳定，再考虑离线模型与桌面打包。

## 4. 风险与应对

### 4.1 风险：系统复杂度过早膨胀

应对：
- 统一后端栈，不并行维护多套业务后端。
- LangGraph 作为唯一主编排入口。
- 默认像素经营桌面与现代信息面板只是视觉层，不改动业务结构。

### 4.2 风险：Agent 自主性过高导致不可控

应对：
- 敏感操作必须进入审批流程。
- 任务拆解和工具调用保留人类确认节点。
- 对外部文件和模型配置的写入保留审计。

### 4.3 风险：画布表现与业务状态脱节

应对：
- 业务状态以事件驱动画布刷新。
- 画布只做状态表达，不作为唯一真相来源。
- 角色形象、移动路径和协同站位都由状态驱动，避免纯装饰动画与业务语义分离。

### 4.4 风险：知识库污染或记忆过载

应对：
- 记忆抽取必须可回看、可撤销、可审批。
- 公司 / 团队 / 个人三层隔离，默认最小可见性。

## 5. 版本门禁

### MVP 门禁

- 初始三人组可创建和运行。
- 任务看板可全流程流转。
- 模型池可统一配置。
- 画布可正常显示状态和工位。

### Beta 门禁

- 会议系统可产出摘要和任务。
- 办公室扩容可稳定触发。
- 文档中心可自动归档。
- 审批与审计可追溯。

### Release 门禁

- 桌面端可稳定打包。
- 本地数据重启后可恢复。
- 离线与在线模型切换正常。
- 性能和错误恢复满足基本日常使用。
